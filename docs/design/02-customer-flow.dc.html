The payment question

One screen, three ways to pay, no dead ends

Most QR ordering systems break here: the guest is thrown to a hosted gateway page in a new tab, loses the table session, and comes back to an app that has forgotten them. Al Bustan never leaves the app. The gateway is embedded as fields inside our own card — QResto type, QResto radius, QResto focus ring — and only the iframe boundary around the card number differs, invisible to the guest.

Pay now · card / wallet
Wallet buttons sit above the fold — one tap, biometric, done. Card fields only expand when the guest picks card, so the default state is short. On success the CTA morphs in place into the status trail; no redirect, no confirmation page.
Cash to waiter
Same button, different verb: "Send to the kitchen". A saffron banner sets the expectation that the order is unpaid, and the same saffron appears on the waiter's ticket and the table tile until settled.
Card at the table
Pings the waiter to bring the terminal, with an ETA on the guest's status screen. When the POS clears, the guest's screen flips to Paid without them touching anything.
Failure is inline, never a new screen — the card keeps its values and the CVC field takes focus. Tips and splits recalculate the same total block; the number never moves position. Every method ends on the same status screen, so the mental model is one flow with a branch.
